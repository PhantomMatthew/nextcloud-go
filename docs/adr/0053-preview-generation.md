# ADR-0053: Phase 4g image preview generation

- **Status**: Accepted
- **Date**: 2026-09-22
- **Deciders**: Project lead
- **Supersedes**: (none)

## Context

Nextcloud clients (web UI, mobile galleries) request scaled-down previews of
image files via `/index.php/core/preview` and `/index.php/core/preview.png`.
PHP Nextcloud generates these on demand and caches them under
`appdata_<instanceID>/preview`. ncgo had no preview endpoint, so every
client gallery view falls back to downloading originals — wasteful and slow.

Constraints shaping the design:

- Preview access must equal read access, including shares. `files.DAV.Read`
  already enforces ownership, incoming shares (user/group, OCM), and public
  mounts; routing preview reads through it inherits all of that.
- Server-side encryption (ADR-0052) and E2EE folders mean a nontrivial share
  of stored content is opaque to the server. Previews must never become an
  oracle that distinguishes "missing" from "unreadable/encrypted", and must
  never fall back to serving source bytes when parsing fails.
- Decoding attacker-controlled images is a memory/CPU risk (decompression
  bombs), so bounds must be enforced *before* pixel decoding.
- The project avoids new dependencies; this phase got an explicit exception
  for `golang.org/x/image` (scaling quality) and `golang.org/x/sync`
  (singleflight; already an indirect dependency).

## Decision

1. **Endpoint surface.** `GET /index.php/core/preview` and
   `GET /index.php/core/preview.png` — the exact paths existing clients use —
   both served by one handler (`internal/preview.Generator`). Query
   parameters: `file` (required DAV path, normalized via
   `files.NormalizePath`; traversal or the root → 400), `x`/`y` (box edges;
   absent → 32; non-integer or < 1 → 400; > `previews.max_dimension` →
   clamped, not rejected, matching PHP behaviour). `mode` is ignored in v1:
   scaling is always an aspect-preserving **fit** into the box, never
   upscaling. Fill/crop modes are deferred.

2. **Auth: `webdav.Auth(authCfg)`, same as DAV routes.** The shared
   `authCfg` chains Bearer tokens, Basic (app passwords), and the
   `nc_session_id` session cookie (`auth.Middleware` tries them in that
   order), so browser sessions and mobile basic-auth both authenticate.
   `ocs.Auth` was rejected: its failure path renders an OCS XML/JSON
   envelope, which is meaningless inside an `<img>` tag, and OCS clients
   signal via `OCS-APIRequest` headers the preview endpoint has no use for.
   The WebDAV-style 401 (empty body + `WWW-Authenticate: Basic`) is the
   right shape for an image resource. The handler additionally 401s when no
   principal is in context (belt and braces).

3. **Content sniffing, never the extension.** The source is opened through
   `DAV.Read` (the access gate; its entry also supplies the etag). The first
   ≤512 bytes go through `http.DetectContentType`; only `image/jpeg`,
   `image/png`, and `image/gif` proceed. Everything else — text, PDFs,
   E2EE blobs, encrypted garbage — gets a uniform **404**. There is no
   fallback-to-original path: serving source bytes for a failed parse would
   leak ciphertext-adjacent content and turn the endpoint into a type-confusion
   oracle. GIFs decode their first frame (stdlib `image/gif` behaviour via
   `image.Decode`) and are re-encoded as PNG.

4. **Bomb guard before decoding.** `image.DecodeConfig` (header only) runs
   first; sources claiming dimensions outside 1..8192 per edge → 404 without
   decoding a single pixel. The source read is additionally capped at
   256 MiB (`io.LimitReader`); over the cap or any decode error → 404.

5. **Cache layout in the configured storage backend.** Previews live under
   `appdata_<instanceID>/previews/` — a sibling of the plugin prefix from
   ADR-0042 — inside the same default `storage.Storage` the app opened
   (so when server-side encryption is enabled, cached previews are sealed
   like any other content). The cache file name is
   `sha256(uid "\n" path "\n" etag "\n" "<x>x<y>")` hex + `.jpg`/`.png`.
   Because the source **etag** is part of the key, any content change
   invalidates implicitly: a rewrite produces a new key, the old entry
   becomes unreachable garbage, and no explicit invalidation pass is needed.
   Stale-entry garbage collection is a listed follow-up. Responses carry
   `Cache-Control: private, max-age=86400` and an `ETag` header set to the
   cache key.

6. **Singleflight generation.** Cache misses generate under
   `singleflight.Group` keyed by the cache key, so a gallery burst of N
   concurrent requests for the same preview triggers exactly one decode +
   scale + encode. Followers receive the generated bytes from the flight
   result — byte-identical to what the leader wrote to the cache — rather
   than re-opening the cache file, which keeps them correct even if the
   cache write failed (write failures are logged, not fatal; the preview is
   still served). The flight re-checks the cache first, covering the
   "another request filled it while we waited" case.

7. **Scaling and encoding.** `golang.org/x/image/draw.ApproxBiLinear` (the
   approved dependency exception: the stdlib has no image resampler, and
   nearest-neighbour thumbnails look unacceptable). Output format: JPEG
   quality 85 when the source is JPEG, PNG otherwise (preserves GIF/PNG
   transparency). Re-encoding also strips source metadata (EXIF), a privacy
   plus. Dimension math is pure `int` (sources ≤ 8192²), so no overflow
   concerns.

8. **Configuration.** `previews.enabled` (default true) gates route
   mounting; `previews.max_dimension` (default 2048, validation bounds
   32..4096) caps the request box. No per-user or per-mime settings in v1.

## Alternatives Considered

### Generating previews eagerly on upload (background job)
- Pros: first request is always a cache hit; decode cost is spread out.
- Cons: generates previews for files nobody ever views; needs a jobs hook
  into `files.uploaded` and invalidation bookkeeping. Lazy + singleflight
  covers the hot path with far less machinery. Deferred as a follow-up cron
  job once usage data justifies it.

### Trusting the filecache MIME / extension instead of sniffing
- Pros: skips the 512-byte read.
- Cons: the filecache MIME is uploader-supplied and unreliable; a renamed
  executable would decode-fail anyway, and a wrong "image/*" claim is
  exactly the oracle we refuse to build. Sniffing is cheap and definitive.
  Rejected.

### Third-party imaging library (bild, disintegration/imaging)
- Pros: more filters, nicer API.
- Cons: heavier dependency for one resampler; `x/image/draw` is
  semi-standard, maintained alongside the stdlib, and sufficient.
  Rejected.

### Serving originals when the requested box ≥ source size
- Pros: saves one re-encode.
- Cons: serves source bytes (EXIF and all) through a "preview" path and
  complicates the never-serve-source rule. Re-encoding at original size is
  cheap and uniform. Rejected.

## Consequences

- New direct dependencies: `golang.org/x/image` (approved exception, this
  increment only) and `golang.org/x/sync` (promoted from indirect).
- New config surface: `previews.enabled`, `previews.max_dimension`.
- Preview cache grows unboundedly with distinct (etag × box) combinations;
  stale entries are orphaned on file rewrite/delete until a GC follow-up
  lands. Keys are content-derived, so there is no correctness issue, only
  storage usage.
- E2EE/encrypted blobs 404 uniformly with missing files — clients already
  tolerate missing previews (they fall back to placeholders).
- Every preview request calls `DAV.Read` (etag + authz gate) even on cache
  hits, but on hits no source bytes are consumed.

### Follow-ups (explicit, not in v1)

- **Document/office previews** via an external service (Collabora/OnlyOffice
  rendering pipeline) — deferred scope.
- ~~**Fill/crop `mode`** support (aspect-fill with center crop).~~ (**fill resolved by ADR-0086**; offset `crop` remains unsupported and falls back to fit)
- ~~**Preview pre-generation cron** on upload events for hot sizes.~~ (**resolved by ADR-0084**)
- ~~**Cache GC** of orphaned etag-keyed entries.~~ (**resolved by ADR-0085**)
- ~~**WebP** input~~/output once `x/image/webp` decode coverage is sufficient. (**input resolved by ADR-0087**; output remains, pending an approved encoder)

## Verification

- `internal/preview/preview_test.go`: real localfs storage + sqlite files
  DAV; generated 800×600 PNG / 400×300 JPEG / 200×100 GIF uploaded via
  `DAV.Write`; fit-box scaling with aspect preservation and decoded output
  dimension checks; JPEG-in → JPEG-out, GIF → first-frame PNG; default 32
  box; never-upscale; `max_dimension` clamping; cache hit (counting source
  proves zero source bytes re-read, byte-identical body, exactly one cache
  entry); etag invalidation on rewrite; 404 for missing file, text file,
  encrypted garbage, foreign user, and a hand-crafted 50000×50000 PNG IHDR
  bomb (CRC-valid, rejected at DecodeConfig before pixel decode); 400 for
  missing/invalid `file`, `x`/`y` ≤ 0, non-integers, and path traversal;
  401 without a principal.
- `internal/config` tests cover the `previews.*` defaults and the
  32..4096 validation bounds.
- `go build ./...`, `go test ./...` green, `go test -race` clean,
  `golangci-lint run ./...` 0 issues, `go mod tidy` clean.
